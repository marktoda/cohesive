## Important issues

### I1. Validator check 13 grep can be silently bypassed by anti-pattern phrasing not in its allow list

- **Severity:** Medium
- **Category:** Enforcement
- **Risk:** The grep at `scripts/validate_plugin.sh:236-245` scopes out lines containing `` ``` ``, `<!-- anti-pattern`, `Anti-pattern:`, or `Hardcoded paths`. Future contributors writing anti-pattern docs will reasonably write "Forbidden:", "Don't do this:", "Bad example:", "Wrong:", "Counter-example:", etc. — none of those will be excluded. The result: a contributor adding a hardcoded-path anti-example outside a fenced block trips the rule on its own documentation. The maintainer's tempting fix is to widen the exclusion list, which silently re-opens the bypass for legitimate violations. The rule needs a positive convention (e.g., "anti-pattern lines must live inside fenced blocks or in a `<!-- anti-pattern -->` HTML comment").
- **Substrate artifact:** Named invariant doc (`PLUGIN_ROOT_PATHS.md`) + linter spec (`validate_plugin.sh`).
- **Suggested repair:** In `docs/substrate/invariants/PLUGIN_ROOT_PATHS.md` §"Known bypass risks," name the exact authoring rule contributors must follow ("Anti-example lines must live inside fenced code blocks **or** be marked with the literal `<!-- anti-pattern -->` comment on the same line"). Then narrow the validator's exclusion list to match exactly that contract.

### I2. Validator check 12 detects presence in source but not emission at runtime

- **Severity:** Medium
- **Category:** Enforcement
- **Risk:** `validate_plugin.sh:227` greps for the literal `^### Recommended next Cohesive skill` heading anywhere in a SKILL.md. In each rewritten skill the heading appears inside a fenced code block in the "Output format" section — i.e., it's part of the rendered template, not the skill body. A skill author could move that heading into the body itself and remove it from the rendered template; the grep would still pass, but the skill would never emit the footer. The conventions doc tells authors the footer is what the skill *produces*, but the linter is checking what the skill *contains*. This is the "presence-as-behavior" enforcement gap — the same shape as the original PLUGIN_ROOT_PATHS gap before this rewrite closed it.
- **Substrate artifact:** Linter spec + conventions doc (`skill-conventions.md`).
- **Suggested repair:** Either (a) tighten the grep to require the heading inside a fenced code block under an `## Output format` H2, or (b) acknowledge in `skill-conventions.md` that the check pins source presence rather than runtime emission and add an explicit reviewer-time check that the heading is inside the rendered output block.

### I3. Audit-substrate's Step 0 announce-then-question ordering is implicit

- **Severity:** Low
- **Category:** Spec drift
- **Risk:** `audit-substrate/SKILL.md:14-23` makes the canonical clarifying question Hard Constraint #1; Step 0 (`:28-37`) resolves the artifact directory and announces it. The body doesn't say which happens first when invoked directly. If Step 0 announces a path before the user has answered whether discovery already happened, the announcement is premature; if the question precedes Step 0, the dispatch announcement comes after a user round-trip. Peer skills (`brainstorm-design`, `rewrite-specs`, `validate-rewrite`, `review-codebase`) each pin Phase/Step 0 ordering implicitly via section order, but `audit-substrate` puts the canonical question in Hard Constraints (above Process) and Step 0 inside Process. A future contributor reading only this file can't tell which the skill does first.
- **Substrate artifact:** Skill body + a one-line addition to `skill-conventions.md`.
- **Suggested repair:** Add a one-line sequencing note: "When invoked directly, ask the canonical prereq question first; resolve the artifact directory only after the user confirms (or `discover-substrate` runs)." Better: standardize the convention across all five Step-0 skills so the ordering is stated once.

## Substrate gaps

- **Negative-trigger phrase list lives in two places.** The list is in `validate_plugin.sh:165-170` and in `docs/substrate/gotchas/discovery-vs-superpowers.md:53-57`. The gotcha doc says it's the canonical list; the validator hardcodes it. If a fifth phrase ever needs adding, both must change in lockstep, and there's no enforcement that they match. Worth a one-line "single-source-of-truth" note in the gotcha doc plus a comment in the script pointing back at it.
- **No explicit row-precedence test for `artifact-placement.md`.** The matrix asserts row A wins over rows B–F when both `docs/history/` and `docs/adr/` coexist (line 30); the ledger flags this as a judgment call (Remaining ambiguity bullet 4). A scenario test or an `audit-substrate` finding category for "duplicate canonical layouts" would make the precedence rule visible to users whose repos straddle both shapes.

- **`PLUGIN_ROOT_PATHS.md` rewritten in present tense.** The "Current state / Intended state" bifurcation is gone; the doc now says what the system *does*, and the validator backs it up. This was the project's own thesis-violating failure mode and the rewrite closes it cleanly.
- **`artifact-placement.md` is genuinely cell-complete.** Eight repo shapes × three artifact categories with explicit precedence and cross-references to the four-rule procedure. An agent encountering a new repo can resolve the directory without reading any prose.
- **`audit-substrate`'s Hard Constraint #1 brought into compliance with peer subskills.** The "auto-detect from session memory" anti-pattern named in `soft-prereqs.md` was still live in this skill; the canonical forced-choice question replaces it. This is the right kind of substrate repair — fix the one outlier rather than weaken the convention.
- **Validator output prefix change (`[FAIL]/[WARN]/[OK]`).** Drive-by, but it removes the `skill-conventions.md` "no emojis" rule contradicting the validator script that enforces it.
- **`skill-section-presence.md` surfaced a real drive-by fix (the missing `What this skill is *not*` section in `validate-rewrite`).** That's the matrix doing its job — making absence visible.
